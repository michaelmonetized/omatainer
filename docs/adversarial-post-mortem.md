**Omatainer: The DAW That Passed Every Test and Forgot to Stop Playing**

*An adversarial source audit of 0.1.0, commit `cae546c7bc840ec1a643e4befe18f91e86d0e4c7`, September 30, 2026.*

Omatainer promises “one clock, one mixer, one window.” After tracing the entry points, I would add: one very optimistic definition of “working.”

Its thirteen existing tests pass. Its built-in crate cannot take the GUI loading path those tests supposedly protect. Its MIDI clock is rejected before reaching the clock handler. Its freshly initialized, stopped engine emits a nonzero constant signal. And a request for scene nine walks straight off an eight-scene array in an application configured to abort on a release panic.

This is a post-mortem of implementation gaps, not a claim that a particular live performance failed. Three independent subagents audited audio/DSP, GUI workflows, and MIDI/CLI/shell integration; a fourth pass reproduced cross-cutting failures. The review covered every shipped entry-point family. The measurements below come from local, isolated probes of this checkout. No physical controller, production audio stream, desktop installer, or Quickshell session was exercised. [The evidence bundle](evidence/README.md) records the coverage, methods, outputs, and reproduction commands.

The first problem is that the README is describing a more complete application than the source contains. It advertises an arrangement timeline, a compose piano roll, and keyboard shortcuts for scene launch, sync, crossfading, view switching, and loading. The actual renderer draws the decks, sampler, crate, and either the session grid or FX panel. There is no arrangement or piano-roll renderer. `View::Arrange` and `View::Compose` exist as enum variants, which is an inexpensive way to own the nouns without implementing the experiences. The keyboard handler omits `1–8`, `W`, `O`, brackets, `Tab`, and `F`. Pad-based note insertion does exist; it is not the advertised piano roll. [README](../README.md#L3), [view declarations](../src/engine/mod.rs#L20), [render path](../src/ui.rs#L223), [keyboard handler](../src/ui.rs#L276).

Nor does this checkout provide project save, project open, autosave, or audio export. Startup constructs a fresh demo. Serializable clip structs and a configuration directory do not amount to a persistence workflow. Calling this a “one document” DAW asks users to invest creative work in a document that has no implemented way to survive closing the program. That is an unfinished product boundary, not a missing cosmetic flourish. [Startup](../src/engine/mod.rs#L1942), [demo initialization](../src/engine/mod.rs#L518), [unused configuration helper](../src/theme.rs#L260).

The built-in crate offers a miniature of the entire problem. The engine has a real `LoadBuiltin` command, and its contract test passes. The GUI identifies built-ins using `path.starts_with("builtin:")`. But these are filesystem paths such as `builtin:drums`; `Path::starts_with` compares path components, not string prefixes. The check returns false. Both built-in entries go to the file decoder as pretend filenames. Our headless probe ran the original `load_sel` method and observed zero engine commands and two decoder jobs. The decoder then attempts to open those paths as files. Any resulting load failure is assigned to `self.status`, which the UI never displays. The test approves the engine; the user operates a different path. [Loader](../src/ui.rs#L132), [decoder](../src/engine/dsp.rs#L616), [contract test](../src/engine/mod.rs#L2252).

Search has the opposite problem: it does too much. The global key handler runs without checking text-input focus. In an egui probe with confirmed search focus, typing `q` inserted the character and emitted `DeckPlay { deck: 0 }`. Letters used for deck control, and spaces used for transport, retain those powers inside the search box. A DJ should not need to consider the musical consequences of spelling a filename. [Update ordering](../src/ui.rs#L212), [unconditional shortcuts](../src/ui.rs#L276), [search field](../src/ui.rs#L569).

Then there is the library’s approach to scale: reconstruct everything, every frame. It filters the collection, clones and formats strings for every matching item, and visits every row inside `ScrollArea::show`. Scrolling clips the view; it does not make this loop virtualized. A synthetic headless run of the original crate renderer, with a fixed 1440 × 108 viewport, two warm-up frames and ten measured frames, produced these median elapsed renderer times:

| Synthetic crate size | Elapsed time per crate frame |
| --- | ---: |
| 100 tracks | 0.170 ms |
| 10,000 tracks | 22.074 ms |
| 50,000 tracks | 116.694 ms |

Those are local `opt-level=1` headless renderer measurements, not release FPS or a GPU benchmark. They establish the scaling problem without pretending to measure desktop smoothness. The application requests continuous repaint while playing, so this work sits precisely where a live music tool wants predictable UI cost. Startup and the Scan button also traverse the music directories synchronously. [Full-row construction and traversal](../src/ui.rs#L588), [repaint policy](../src/ui.rs#L267), [filesystem scan](../src/ui.rs#L78).

The audio callback is an even more enthusiastic customer of the allocator. For each output frame, each active MIDI track clones its entire note vector. An arpeggiated track also constructs, sorts, and deduplicates a chord vector. Each nonempty FX chain clones its slot vector per sample, including when the slots are disabled. These are operations in the renderer, not occasional project edits. [Track rendering](../src/engine/mod.rs#L749), [FX processing](../src/engine/fx.rs#L132).

An instrumented allocator around 1,024-frame calls to the actual renderer counted:

| Workload at 48 kHz | Allocation calls | Requested allocation bytes |
| --- | ---: | ---: |
| Idle, after initialization | 0 | 0 |
| Default scene: four active MIDI clips, 30 notes total | 4,096 | 368,640 |
| One compressor slot on each of eight stopped tracks | 8,192 | 196,608 |
| One active arpeggiated chord clip | 3,072 | 106,496 |

Four note-vector allocations per frame imply 192,000 allocations per second at 48 kHz, before adding effects or periodic snapshot publication. These bytes measure allocation traffic, not retained memory. The measured blocks themselves completed inside their time budgets on this machine; that does not erase the dependence on allocator behavior or the growing per-sample scan cost. A real-time callback should not need a favorable relationship with the heap to keep time.

The synchronization design provides two more routes to trouble. GUI commands can take the engine mutex, mutate state, and publish a snapshot. The audio callback uses `try_lock`; if the mutex is unavailable, it sends the already-zeroed buffer to the device. That is an explicit whole-buffer silence path. When audio does acquire the engine, its periodic publication takes a blocking snapshot mutex. The UI and IPC readers use that same snapshot mutex. [GUI command dispatch](../src/engine/mod.rs#L1957), [callback](../src/engine/audio.rs#L50), [publication](../src/engine/mod.rs#L1592).

We deliberately held the snapshot lock for 80 ms and rendered a 512-frame block crossing a publication boundary. The renderer took 80.105 ms against a 10.667 ms block budget. This is a contention reproduction, not an observed live-device underrun. Worse, the engine calculates its CPU metric before publication, so the stall is excluded from its own report. A separate one-frame contention probe waited roughly 50 ms while the published CPU fraction remained only a few percent. The expensive part can happen after the stopwatch has declared victory. [Timing and publication order](../src/engine/mod.rs#L740).

Even when the renderer runs quickly, its transport semantics are unreliable. Launch a quantized one-shot at beat 0.25: the command schedules it for beat 1. The renderer immediately computes `(beat - start_beat).rem_euclid(clip_beats)`, with no pending-launch guard. Time before the start becomes time near the end of the clip. Our note was already active at beat 0.250043. The one-shot was gone by beat 1.111154, after interpreting the scheduled start as a loop wrap. Quantization has become a time machine with an early exit. [Launch scheduling](../src/engine/mod.rs#L1033), [playback position](../src/engine/mod.rs#L752), [one-shot termination](../src/engine/mod.rs#L814).

Note ownership fares no better. A live note-on goes to the selected track; note-off goes to whichever track happens to be selected later. Hold a note, change selection, release it: the original voice remains held. Stopping a scene removes its playing-clip state without releasing its voices. Both probes still found the old voice in sustain after two seconds of rendering. These are reproduced state-lifecycle failures, not a complaint about intentional reverb tails. [Live-note routing](../src/engine/mod.rs#L1299), [scene stop](../src/engine/mod.rs#L1456).

Deck stop has its own interpretation of silence. The playhead stops advancing, but the renderer continues reading the sample at the frozen position. The default initialized engine, with session and both decks stopped, produced a constant left and right output of approximately `0.0650975`. A synthetic paused deck made the mechanism equally clear. This is nonzero DC in the generated buffer; whether a particular output device blocks DC or produces an audible transient was not tested. The software boundary is already wrong. [Deck rendering](../src/engine/mod.rs#L902), [unconditional sample read](../src/engine/mod.rs#L925), [keylock’s stopped branch](../src/engine/mod.rs#L958).

Stereo processing compounds the confusion. Left and right deck samples pass through the same stateful EQ and filter objects. The master also ticks the same delay and reverb instances twice per stereo frame. A left-only signal acquired right-channel output after EQ; a master echo configured for 18,000 samples appeared after 9,000 stereo frames. These probes explain why independent channel histories matter more than having two floating-point variables named `l` and `r`. [Deck effects](../src/engine/mod.rs#L936), [master effects](../src/engine/mod.rs#L727).

The FX panel has plenty of movement, but movement is not a contract. Every effect gets three parameter sliders whether its implementation reads those parameters or not. Sweeping the delay’s first parameter from zero to one left its first echo at sample 12,000. Two delay slots share one delay instance rather than owning independent state. Balance at zero wet mix still panned fully left in a probe. Scene-specific FX panels all edit the same global `scene_fx` chain. A panel labeled “scene 2 fx” showed the slot added only through scene 1. This is exactly the kind of label-to-behavior mismatch the project’s own contract says is a bug. [FX controls](../src/ui.rs#L806), [DSP dispatch](../src/engine/fx.rs#L139), [shared chain selection](../src/engine/mod.rs#L1582), [control contract](../CONTRACT.md#L1).

MIDI’s “first-class” treatment is mostly a collection of first drafts. The input handler rejects messages shorter than two bytes before handling system real-time messages. Our one-byte Start, Stop, and Clock inputs all produced zero commands. The clock branch itself is empty; clock-output functions have no callers. MIDI learn has no UI path that arms it, and the engine’s `LearnCapture` handler is empty. Artificially arming learn in a probe caused incoming controls and notes to be swallowed into discarded capture commands without completing learning. The latter is evidence about the unfinished implementation, not a currently reachable learn button. [Input parser](../src/engine/midi.rs#L196), [clock output helpers](../src/engine/midi.rs#L177), [empty learn handler](../src/engine/mod.rs#L1359).

The implemented controller paths are not all safer. The APC40 map repeats channel-zero CC7 across all eight track faders, and dispatch visits every match. One input, `B0 07 7F`, generated track-gain updates for `[0, 0, 1, 2, 3, 4, 5, 6, 7]`. The relative jog decoder produced no negative jog delta for any of its 128 possible data bytes. A Pioneer load binding emitted `DeckLoadSelected`, whose engine handler does nothing beyond a comment saying the UI resolves the path. No such bridge consumes it. We tested the software mappings with synthetic messages, not the physical devices. [APC40 map](../src/engine/midi.rs#L645), [relative decoding](../src/engine/midi.rs#L294), [load stub](../src/engine/mod.rs#L1247).

The command-line control surface contributes the sharpest failure. `omatainer ctl scene 9` becomes zero-based scene 8. The server accepts that index and `LaunchScene` uses it without bounds checking against the eight-element clip array. An isolated engine probe confirms the panic. A second harness compiled with the release profile's `panic = "abort"` strategy exited with `SIGABRT`. Source tracing connects the ordinary CLI request to that aborting engine path; no running desktop or audio process was crashed. [CLI conversion](../src/main.rs#L101), [IPC dispatch](../src/main.rs#L178), [unchecked array access](../src/engine/mod.rs#L1058), [release profile](../Cargo.toml#L31).

Meanwhile, malformed JSON and unknown operations receive `"ok": true`. The shell follower even sends bare `status`, not the JSON request used by the ordinary status command, and gets away with it because parsing errors are converted to an empty object and acknowledged. It opens a fresh socket every 250 ms; the server creates a fresh thread for every connection. That is roughly 14,400 connections and handler threads per hour for one follower, before request time is counted. No catastrophic CPU overhead was measured here; it is needless polling and thread churn where the name “follow” suggests a subscription. [Follower](../src/main.rs#L74), [thread creation](../src/main.rs#L144), [parser and response](../src/main.rs#L169).

Single-instance detection can make that interface disappear. A connected instance gets 200 ms to answer; any resulting I/O error causes its socket pathname to be removed as “stale.” A deliberately delayed live listener reproduced the unlink. A slow instance can therefore lose its discoverable control socket and permit a second launch attempt. Installation is similarly optimistic: it writes multiple files in place, suppresses Hyprland reload and configuration-error failures, and prints “done.” Its theme-reload hook calls an operation that is simply an alias for status. Those installer observations are source review, not a test against the user’s desktop. [Instance check](../src/main.rs#L44), [installer](../scripts/install-omarchy.sh#L102), [reload alias](../src/main.rs#L111).

The causal pattern is remarkably consistent. Features have declarations without reachable workflows. Tests invoke internal commands while the GUI takes a broken route. Stateful operations lack ownership across selection changes, channels, scenes, and effect slots. Success responses describe receipt rather than successful execution. Performance work is delegated to the allocator, the mutex scheduler, and the hope that a music library stays small.

There is real implementation here: synthesis, sample decoding, decks, pads, effects, and a working set of internal contract tests. That makes the gaps more consequential. The application is capable enough to invite use while its boundaries remain capable of silently doing the wrong thing.

The repair order should reflect that reality: reject invalid control input; make stop and note-off release the correct voices; distinguish pending clips from running ones; establish independent channel and effect state; remove allocation and blocking publication from the audio path; make crate rendering depend on visible rows; and test GUI, MIDI, and IPC routes through to their effects. Then either implement the advertised editing and persistence workflows or reduce the claims. The thirteen passing tests can remain. They need company at the places where users actually enter.

Until then, Omatainer’s most polished cross-cutting feature is confidence. The README has it. The JSON replies have it. The green tests have it. The audio engine is still waiting for its turn.
